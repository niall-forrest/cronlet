Cronlet Cloud is a managed scheduler and wake-up service. Its production guarantee is:

**At-least-once scheduled delivery attempts.**

Cronlet guarantees that every due schedule creates durable delivery records:

- `Run`
- `RunAttempt`
- `DispatchJob`

Dispatch is retried until success, cancellation, timeout, retry-window expiry, or dead-letter.

Cronlet does not guarantee exactly-once callback effects. Your application must dedupe with `run.id`, `attempt.id`, `task.externalId`, `callbackDeliveryId`, or a business key such as `emailSendId`.

Cronlet is designed so your application can reconcile its own business state against Cronlet state instead of treating Cronlet as the source of truth.

## Outbound guardrails

Cronlet validates outbound webhook and callback destinations at delivery time.

- `http` and `https` are allowed
- `localhost` and `*.localhost` are blocked
- private, loopback, link-local, and cloud-metadata IP ranges are blocked
- DNS is resolved at execution time before delivery
- redirect hops are revalidated before Cronlet follows them

If you set `CLOUD_ALLOWED_OUTBOUND_HOSTS`, Cronlet also requires every outbound destination hostname to appear in that allowlist.

Organizations can also maintain their own outbound hostname allowlist with `GET /v1/outbound-policy` and `PATCH /v1/outbound-policy`. When both are configured, Cronlet uses the intersection so the org policy can only narrow, never widen, the process-level policy.

Callback verification secrets are also rotatable with `POST /v1/callback-signing-secret/rotate`, and Cronlet records the rotation in audit history.

## Secret protection

Cronlet stores secret values encrypted at rest and records encryption metadata per secret.

- values are encrypted with authenticated encryption before persistence
- each secret stores its `keyVersion` and `lastRotatedAt`
- Cronlet can rotate existing secrets onto the active encryption key without changing the plaintext value

Configure cloud key material with `CLOUD_SECRET_ENCRYPTION_KEYS` using versioned entries such as `v1:<base64-32-byte-key>,v2:<base64-32-byte-key>`.

## Success semantics

For webhook delivery, Cronlet treats HTTP `2xx` as success.

Default retry behavior:

- `408`, `409`, `425`, `429`, and `5xx` are retryable
- network errors, DNS errors, connection resets, and timeouts are retryable
- `400`, `401`, `403`, `404`, `410`, and `422` are terminal client errors
- `3xx` redirects are not followed unless `followRedirects` is enabled on the webhook handler

Tasks can override this with `retryOnStatusCodes` and `terminalStatusCodes`.

## Retry policy

Cronlet stores retry state in durable dispatch records. Process restarts do not erase retry state.

Default policy:

- max attempts: `10`
- initial delay: `10s`
- max delay: `15m`
- retry window: `24h`
- backoff: exponential
- jitter: enabled

When a worker dies mid-delivery, the dispatch lease expires and reconciliation makes the job retryable again.

## Destination protection

Cronlet tracks per-destination circuit breaker state for retryable webhook failures.

- a destination opens after repeated retryable failures
- open destinations stop leasing new deliveries until the cooldown window expires
- after cooldown, Cronlet half-opens the destination and allows one probe attempt
- a successful probe closes the breaker
- a failed probe re-opens the breaker and defers sibling deliveries for that destination

Operators can inspect current breaker state with `GET /v1/circuit-breakers`.

Cronlet also records explicit dispatch events for:

- circuit breaker open, half-open, and close transitions
- outbound-policy-blocked delivery attempts
- reconciliation repairs after expired leases

These events flow through task and run timelines so operators can see why delivery paused, resumed, or was blocked.

## Fairness

Cronlet applies bounded lease fairness when dispatching due work:

- due dispatches are leased in small batches
- leasing is spread across organizations instead of letting one org consume the whole batch
- concurrency is capped per organization and per destination key

This keeps one noisy customer or one hot endpoint from monopolizing the worker fleet.

## Cancellation

`tasks.cancel(taskId)` cancels pending and retry-wait dispatches, clears `nextRunAt`, and prevents new attempts from starting after the API returns.

If an attempt has already started, Cronlet returns the running attempt IDs and reports `guarantee: "no-new-attempts"`.

## One-off schedules

One-off schedules are first-class:

```ts
await cronlet.tasks.create({
  name: "Send onboarding step 2",
  externalId: "emailSend_123",
  schedule: {
    type: "once",
    at: "2026-05-07T09:00:00.000Z",
  },
  maxRuns: 1,
  metadata: {
    orgId: "org_123",
    appId: "app_123",
    contactId: "contact_123",
    emailSendId: "emailSend_123",
    emailStepKey: "onboarding.step_2",
  },
  handler: {
    type: "webhook",
    url: "https://platform.example.com/internal/email/send",
  },
});
```

For customer-facing email or billing workflows, keep canonical state in your application and use Cronlet as the durable wake-up layer. Store the Cronlet task ID and use an overdue-send reconciler in your own system.

## Reconciliation APIs

Cronlet exposes metadata-first control-plane APIs for product reconciliation:

- `tasks.list(...)` supports filtering by `externalId`, metadata, schedule type, active state, and next run time
- `runs.list(...)` supports filtering by task, run status, `externalId`, metadata, and scheduled time
- `tasks.bulkCancel(...)` cancels many matching tasks in one request
- `runs.bulkReplay(...)` replays matching runs without mutating historical records
- `reconciliation.compare(...)` returns:
  - matching tasks
  - missing external IDs
  - duplicate external IDs
  - pending one-off tasks
  - overdue tasks

These APIs are intended for application-owned workflows such as email drips, reminders, billing retries, and agent follow-ups where your product stores the canonical entity state and Cronlet provides durable wake-ups.

## Auditability

Cronlet records audit events for mutating control-plane actions such as:

- task create, update, cancel, bulk cancel, delete, and manual trigger
- run replay and bulk replay
- secret create, update, and delete
- API key lifecycle changes

`/v1/audit-events` supports filtering by actor, action, target type, target ID, and time window so operators can ask focused questions like “what changed for this task?” or “who replayed this run?”.

For execution history, Cronlet also exposes timeline endpoints:

- `GET /v1/tasks/:taskId/timeline`
- `GET /v1/runs/:runId/timeline`

These timelines combine durable task, run, and dispatch state transitions with relevant audit events so operators can answer “why did this run fire?”, “why was it replayed?”, or “what changed around this delivery?” from one stream.

## Initial cloud assumptions

Cronlet Cloud starts as a single-primary-region scheduler. Postgres is the authoritative clock and source of truth for due claiming.

Future multi-region workers may execute dispatch regionally, but schedule claiming remains serialized by the primary database or a designated leader.

## Product fit

Cronlet is intentionally not a full durable workflow runtime. Trigger.dev and Inngest are better fits for durable step execution, checkpointing, arbitrary long-running code, and workflow orchestration.

Cronlet is built for products and agents that need reliable scheduled wake-ups, metadata, cancellation, signed callbacks, replay, and reconciliation while keeping business logic in the customer application.
